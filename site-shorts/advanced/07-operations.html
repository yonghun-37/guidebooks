먼저 답부터

처음엔 로컬로 돌리세요. PC를 끄려면 외부 상태 저장을 먼저 준비하고 GitHub Actions로 옮겨요.

새 runner는 새 컴퓨터와 같아요. 어제의 DB·세션·승인을 복원하지 못하면 새 게시를 시작하지 않아야 해요.

도윤하루 한 번 예약하면 실패도 알아서 고치나요?

서진tick이 미완료 상태를 다시 읽어요. 예외나 결과 불명은 사람 확인이 필요해요.

만드는 순서

OS 예약은 mock부터 등록해요

생성 명령은 예약 파일만 만들고, 등록은 출력된 설치 명령을 실행할 때 이뤄져요.

새 터미널이면 Windows에서 A0의 Set-Alias, macOS에서 source .venv/bin/activate를 다시 실행하세요. 생성된 설치 파일은 Python·작업 폴더 절대경로를 담아요. 인수에 토큰을 넣지 않아요. 작업 스케줄러·LaunchAgent의 사용자·절전·로그인 조건을 확인하세요.[A051][A052]

아래 생성 명령 후 출력된 .ps1 또는 .sh 파일을 열어 확인하고, 출력된 등록 명령을 본인 PC에서 실행하세요. Windows는 Get-ScheduledTask, macOS는 launchctl print로 등록을 보고 수동 실행·다음 날 실행을 확인해요. Linux는 --os cron으로 생성해 crontab -l에서 확인해요. 해제는 생성 파일 끝 안내를 따라요.

지금 할 일 mock 등록·실행 로그를 확인한 뒤 --config config.json --live로 새 예약을 만드세요.

tick은 15분마다 상태를 읽어요

지정한 현지 시각 이후 하루 한 번 새 주제를 만들고, 기존 실행은 매 tick 재개해요.

승인 대기는 프로세스를 계속 켜 두지 않아요. APPROVED.json과 상태를 저장한 뒤 다음 tick이 이어 가요. 승인하지 않은 날은 게시하지 않아요. 테스트 모드 토큰 만료 경보·할당량 연기·비용 중단도 일일 보고에서 보세요.

지금 할 일 private/state/execution.log와 dashboard.html을 매일 확인하세요.

runner 밖에 상태를 보관해요

키트 예시는 private 전체를 암호화해 비공개 R2에 보존해요.

GitHub Actions 예시를 본인 저장소의 .github/workflows로 복사하기 전에 README의 상태 초기화를 끝내세요. 로컬 private에는 녹음·소재·OAuth까지 들어가니 공개 artifact나 캐시로 옮기지 마세요.[A046][A155]

R2 상태 bucket은 비공개로 두고 STATE_BUCKET·STATE_ENDPOINT·STATE_ACCESS_KEY_ID·STATE_SECRET_ACCESS_KEY·STATE_ENCRYPTION_KEY를 Secrets에 넣어요. Fernet 암호화 키는 README 명령으로 비공개 파일에 만들고 따로 백업해요. 키를 잃으면 복원할 수 없어요. R2 무료량은 강제 비용 상한이 아니에요.[A048]

보통 이런 이름의 Repository Settings → Secrets and variables → Actions에서 넣어요. 앱이 업데이트되면 버튼 이름이나 위치가 조금 다를 수 있어요. 최신 앱 화면에서 비슷한 이름의 버튼을 찾아 주세요. 못 찾겠으면 공식 도움말을 확인하세요.[A046]

예시의 KIT_CONFIG_JSON에는 비밀 없는 설정 전체를 넣어요. 쇼츠만 운영하면 예시의 KIT_FLOW: ${{ inputs.flow || 'insta' }} 기본을 shorts로 바꾸세요. workflow_dispatch의 flow도 shorts를 골라요. 생성·수동·예약 모두 같은 concurrency 그룹을 유지하고 로컬과 동시에 돌리지 마세요. AUTO_KIT_LIVE 기본은 false예요. 처음에는 예약의 그 값을 켜지 말고 mock 복구부터 시험하세요.

schedule은 최소 5분·timezone 옵션을 지원하지만 지연·누락될 수 있어요. 공개 저장소는 60일 비활성 시 예약이 꺼질 수 있어요. 예시는 UTC cron으로 15분 간격, TZ=Asia/Seoul로 현지 하루 생성을 판단해요. 보장 게시 시각이 필요하면 미리 업로드해 publishAt을 쓰세요.[A044]

지금 할 일 pull → mock 재개 → push를 시험하고, 실제 청구·예약 지연·실패 알림을 확인하세요.

알림과 승인 수신을 구분해요

Discord webhook은 알림부터, 휴대폰 승인은 Telegram polling을 선택하세요.[A066][A067]

notification.json은 로컬에서 항상 남아요. .env의 Discord/Telegram 값은 live 실행 때만 전송해요. Telegram은 TELEGRAM_ALLOWED_USER·TELEGRAM_CHAT_ID를 정해 허용 사용자·채팅·콘텐츠 해시를 확인해요. pipeline.py telegram --live는 최대 25초 응답을 읽고 종료해요. webhook과 polling은 동시에 쓰지 않아요.[A067]

Discord 링크 버튼만으로 승인 응답이 오지 않아요. 수신 앱을 만들면 서명·사용자·중복 검증이 필요해요. 처음에는 알림을 보고 로컬 approve·resume을 쓰세요.[A065][A144]

지금 할 일 알림 실패가 이미 성공한 게시를 재실행하지 않는지 확인하세요.

코드 없이 돌리는 선택지

n8n은 API 연결용 실행기예요. Make·Zapier도 연결을 관리하지만 생성 API 비용·서버·저장소는 별도예요. n8n Community의 내부 자동화 사용료 0과 서버비 0은 다르게 계산하세요.[A120][A055]

Make Free 월 1,000credits, Zapier Free 월 100tasks는 게시물 수가 아니에요. 가상 30편 × 6성공 액션=180액션에 대기·재시도도 더해요. 표시 필드가 노드에 없으면 HTTP 요청 JSON에서 status.containsSyntheticMedia를 직접 설정하고 확인하세요.[A131][A062][A020]

키트 n8n 예시는 Python 실행 환경이 있는 셀프 호스팅용이에요. 쇼츠 flow를 고르고 mock부터 시험하세요. 이 책의 기본 실행 경로는 Python이에요.

해 보기 · 명령 실행

지금 하는 일: OS 예약 파일·일일 보고·상태 복구 계획을 확인해요.

왜 하는지: 앞 단계의 실제 파일과 상태를 읽어 다음 작업을 이어 가기 위해서예요.

아래 명령은 auto-kit 폴더에서 실행하세요. A0에서 가상환경을 먼저 준비해요. RUN_ID가 있으면 앞 명령이 출력한 실제 12자리 ID로 바꿔요. Windows와 macOS는 같은 Python 명령을 써요.

python -m schedule.install --os windows --flow shorts --time 09:17
python pipeline.py report
python -m schedule.install --os macos --flow shorts --time 09:17
python pipeline.py report

이렇게 보이면 성공

예약 파일 생성 완료: 뒤 Windows의 install-shorts.ps1 또는 macOS의 .plist·설치 .sh 위치가 보여요. daily-report.json·dashboard.html도 생겨요. 이 단계는 아직 OS에 작업을 등록하지 않았어요.

비용 · 편당과 한 달

확인할 점

Actions 실행·저장소는 조건별 과금이에요. 표준 공개 runner 무료, GitHub Free 비공개 월 2,000분 조건과 다른 사용량을 확인하세요. 상태 저장 실패 뒤에는 복구를 끝내기 전 예약을 켜지 마세요. 로컬과 Actions를 한 상태로 동시에 운영하지 않아요.[A045]
