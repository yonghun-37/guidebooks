② 실행 장소를 하나 고르세요

로컬 예약은 그 컴퓨터가 켜져 있어야 해요. 재부팅·절전·실행 계정·시간대를 함께 확인하세요. 아래는 생성 파일을 실제 예약으로 바꾸기 전의 선택 과제예요.

예약 도구를 고르는 기준
도구읽을 파일·설정등록 뒤 확인
Windows 작업 스케줄러windows.txt를 읽고 보통 이런 이름의 “작업 만들기”에서 매일 트리거를 정해요. 프로그램은 <KIT>\.venv\Scripts\python.exe, 인수는 "<KIT>\blog.py" report, 시작 위치는 키트 절대 경로로 넣어요.수동 실행 → 마지막 실행 시각·결과 → 작업 기록 확인. 겹치면 새 인스턴스를 시작하지 않도록 설정해요.
Linux croncron.txt의 <KIT>을 실제 절대 경로로 바꿔요. 실행 대상을 blog.py report로 고쳐 사용자 crontab에 등록해요. 예시 0 9 * * *은 매일 9시예요.같은 사용자로 수동 실행 → 다음 실행 뒤 보고서 수정 시각 확인. 표준 출력·오류를 비공개 운영 로그에 저장해요.
macOS launchdlaunchd.plist의 경로를 바꾸고 run·--sample 인수 대신 report 하나를 써요. LaunchAgents 작업으로 등록할 때 출력·오류 로그 경로도 정해요.ProgramArguments의 Python·blog.py 경로와 실행 계정 확인 → 수동 시작 → 보고서·로그 확인.
GitHub Actionsops/github-actions.yml은 수동 실행 예시예요. 아래 외부 상태 보존을 먼저 구성한 뒤 예약 트리거를 추가해요.기본 브랜치의 Actions 실행 로그와 외부 상태 저장 성공을 함께 확인해요.

위 표의 <KIT>은 blog.py가 있는 폴더의 전체 경로예요. 실행 파일·인수·시작 폴더를 구분해 넣으세요. 경로에 공백이 있으면 따옴표를 지키세요. 생성 파일의 run --sample은 가상 승인 시연을 포함해요. 예약 연습은 report로 바꾸고, 실제 승인 작업으로 사용하지 마세요.

앱이 업데이트되면 버튼 이름이나 위치가 조금 다를 수 있어요. 최신 앱 화면에서 비슷한 이름의 버튼을 찾아 주세요. 못 찾겠으면 공식 도움말을 확인하세요: Windows · macOS launchd · crontab.

선택 · GitHub Actions는 상태 보존을 먼저 준비해요

작업이 끝나도 승인·중복 방지 기록이 남아야 해요. runner는 명령을 돌리는 컴퓨터예요. 임시 runner 안의 파일만으로 운영 상태를 보존하지 마세요. 이 키트의 Actions 예시는 외부 상태의 복원·보관을 직접 구성하도록 남겨 두었어요.

외부 저장소에는 private/state.sqlite3의 승인·잠금 기록, 필요한 미디어와 설정을 보관해요. 쓰기 충돌을 막도록 한 실행만 상태를 갱신하게 하세요. 복원 또는 저장 실패 시 다음 발행을 보류해요. 공개 저장소·공개 artifact에 승인 대장·키·아이 사진을 올리지 마세요. 비밀은 Actions Secrets나 별도 비밀 보관소에서 받아요.

예약은 기본 UTC이며, 기본 브랜치의 최신 커밋에서 실행돼요. 지연·누락이 생길 수 있어요. 키트 예시의 concurrency는 같은 작업의 겹침을 줄이는 설정이에요. 서로 다른 컴퓨터의 상태 잠금을 대신하지 않아요.[BX080]

먼저 수동 실행으로 “외부 상태 복원 → 보고서 생성 → 외부 저장 → 다음 실행에서 이어 읽기”를 확인하세요. 그 전에는 발행을 연결하지 않아요.

③ 실패와 승인 대기 알림을 확인해요

실행 로그와 알림 기록을 함께 보세요. 이번 실습은 notifications.json에 승인 대기 사건만 남겨요. 외부 전송과 실패 알림 배선은 아직 연결하지 않았어요.

실패 시 읽는 순서
순서확인할 곳할 일
첫째스케줄러의 마지막 실행 시각·표준 출력·표준 오류실행이 시작됐는지, 어떤 명령에서 멈췄는지 확인
둘째private/terminal.json · output/state.json · private/events.json파일이 있으면 마지막 명령·상태·예약 확인 사건을 대조. 이벤트 파일은 해당 사건 뒤 생겨요.
셋째output/notifications.json발송 대상 사건·날짜·live 값을 확인. 기록이 있다고 수신 성공은 아니에요.
넷째실제 서버의 글 ID·상태예약 여부를 조회해 다음 실행에서 같은 글을 다시 만들지 않아요.

실알림을 연결할 때는 키트 ops/notifications.py의 허용 HTTPS 주소와 전송 함수를 준비해요. 알림에는 사건명·시간·비공개 검토 위치만 넣고, 아이 정보·비밀키·원고 전체를 보내지 마세요. 전송 오류를 기록하고 수신 여부도 직접 확인하세요. 승인 대기 목록은 알림과 따로 남겨요.

미응답이면 그대로 대기해요. 건강·협찬·제휴·아이 사진/경험·기존 글 갱신은 항상 사람 승인이에요. 광고주 확인만으로 최종 승인을 채우지 않아요. 원고·사진·표시가 바뀌면 다시 승인해요.

✔ 통과: SQLite·mock WordPress·설정 복구

다시 private/state.sqlite3와 private/mock-wp/가 생겼는지 보세요. 마지막 체크포인트가 저장된 글·승인 상태와 파일 내용까지 대조해요. 키트 밖으로 옮긴 원본은 통과를 확인한 뒤 정리하세요.

이 ZIP이 되살리는 범위
자료키트 ZIP추가로 보관할 곳
글·승인·중복 잠금·비용 기록SQLite의 논리 덤프 state.sql로 보관비공개 백업 사본. 실행 중에는 쓰기를 멈추고 일관된 시점으로 보관
mock 서버 글·미디어private/mock-wp/ 보관샘플 밖의 원본 사진·작업 원고는 별도 비공개 저장
설정config.example.toml, 있으면 config.toml설정에 비밀을 넣지 않기
코드·샘플·운영 로그이 ZIP의 전체 백업 대상이 아니에요.코드는 Git, 개인 원고·원본 사진·로그는 비공개 별도 백업
비밀번호·토큰.env는 제외해요.접근을 제한한 비밀 보관소. 복구 뒤 필요하면 재발급
실제 WordPress DB·uploads포함하지 않아요.아래 선택 과제에서 호스팅/WordPress 백업을 따로 만들기
선택 · 실제 WordPress는 DB와 uploads를 새 환경에 복원해요

mock ZIP으로 실제 WordPress를 복구할 수 없어요. 로컬 WordPress 또는 본인 호스팅에서만 별도 과제로 진행하세요. 처음에는 운영 사이트에 덮어쓰지 않아요.

  1. 호스팅의 백업·복원 메뉴에서 DB 내보내기와 파일 내려받기를 확인해요. 글·설정이 든 DB SQL 덤프와 같은 시점의 wp-content/uploads를 함께 보관해요. 테마·플러그인·버전·도메인 설정도 기록해요.
  2. 새 로컬 또는 접근 제한 테스트 환경을 만들어요. 공개 트래픽·메일·알림·발행 예약을 끈 상태에서 같은 버전을 준비해요.
  3. 관리 도구로 SQL을 가져오고 uploads를 제자리에 복원해요. 시험 주소로 옮길 때는 호스팅의 이전 도구로 URL을 바꿔요. 직렬화된 DB 문자열을 무작정 치환하지 마세요.
  4. 대표 글의 ID·본문·분류·사진 원본·공개 주소를 대조해요. REST 읽기와 관리자 글 목록이 맞아야 해요. 예약 글·시간대·승인 기록도 확인해요.
  5. 새 비밀키로 읽기 요청부터 확인하고 발행은 보류해요. 복원 파일 목록·일시·확인한 글과 미디어를 기록한 뒤 운영 전환을 결정해요.

키트의 mock 복원 통과와 이 과제 완료를 진행표에 따로 적으세요. 본인 호스팅에서 DB 내보내기·uploads 내려받기·새 환경 복원이 되는지 A2의 연결 점검에서도 확인해요.

⑤ 비밀키가 노출되면 먼저 폐기해요

실행 중단 → 노출 키 폐기 → 새 키 발급 → 로컬 설정 교체 → 읽기 검증 순서예요. 로그에서 글자만 지워도 유출된 키는 계속 쓸 수 있어요. WordPress 애플리케이션 비밀번호는 사용자 프로필에서 개별 폐기하고 새로 발급해요.[BX003]

  1. 예약 작업과 외부 호출을 멈춰요. 어떤 서비스의 어떤 키인지 식별해요.
  2. WordPress·분석 계정·알림 서비스의 공식 관리 화면에서 노출 키/토큰을 폐기해요. 비정상 글·접속·과금 내역도 확인해요.
  3. 최소 권한으로 새 키를 만들고 로컬 .env 또는 비밀 보관소만 교체해요.
  4. 현재 로그·공개 artifact·백업 사본에서 키가 섞인 자료를 찾고 접근을 막아요. 공개 Git 기록에 들어갔다면 현재 파일 삭제와 함께 기록 제거 절차도 진행해요.
  5. 본문·사진을 바꾸지 않는 읽기 요청으로 인증을 확인해요. 권한과 목적지를 검토한 뒤 예약을 다시 켜요.

정기 교체도 같은 순서로 연습하세요. 새 키 값을 터미널 출력이나 보고서에 붙이지 마세요.

⑥ 겹친 실행과 한도 초과에서 멈춰요

새로 만들기 요청을 반복하기 전에 기존 글 ID를 조회하세요. 키트는 SQLite에 실행·내용 잠금과 날짜별 예약 상한을 남겨요. 여러 실행이 같은 SQLite 상태를 쓰면 같은 잠금을 확인해요. 상태를 각자 새로 만들면 이 보호가 이어지지 않아요.

⑦ 예약 성공 뒤 실제 공개를 다시 확인해요

future는 예약이고 publish가 실제 공개 상태예요. WordPress의 WP-Cron은 방문 요청을 계기로 기한이 지난 작업을 실행해요. 방문이 드물면 예약한 시각보다 공개가 늦어질 수 있어요.[BX127]

A6에서 저장한 post_id로 조회하고 공개 URL을 열어 본문·사진·표시를 확인하세요. 늦었다고 같은 글을 다시 만들지 마세요. 서버 스케줄러로 WP-Cron을 실행하는 설정은 호스팅의 공식 안내를 따라요. 공개 상태 조회가 실패하면 완료로 표시하지 않아요.

자주 묻는 질문 6개

노트북이 꺼져도 예약이 도나요?

노트북의 예약은 멈춰요. 계속 켜진 서버나 Actions 같은 실행 장소를 골라요. Actions를 쓰면 외부 비공개 상태 보존부터 구성하세요.

실행이 늦거나 실패하면 어디를 보나요?

스케줄러 실행 기록부터 보고 상태·알림을 대조해요. 예를 들어 예약 시각은 지났는데 로그가 없으면 실행 자체를 확인해요. 표준 출력·오류와 승인 대기 목록을 열어 보세요.

승인 알림을 못 봐도 자동 공개되나요?

아니에요. 응답 없음은 승인 대기예요. 협찬 글은 광고주 확인 뒤에도 최종 사람 승인이 필요해요. 대기 글을 검토하고 바뀐 내용에는 다시 승인하세요.

무엇을 백업하고 복구는 어떻게 확인하나요?

코드·원본 사진·상태 DB·비밀을 나눠 보관하고 새 환경에서 확인해요. 이번 ZIP은 mock DB·미디어·설정이에요. 두 자료를 키트 밖으로 옮겨 복원하고 check를 통과하세요. 실 WordPress는 DB·uploads 별도 과제예요.

API 비밀번호가 노출되면 어떻게 하나요?

실행을 멈추고 노출 키부터 폐기해요. 새 키를 발급해 .env를 바꾼 뒤 읽기 요청으로 확인하세요. 로그·백업·공개 기록 점검도 이어 하세요.

겹친 작업과 한도 초과는 어떻게 막나요?

상태를 공유해 잠그고 한도 초과 시 정해진 횟수 뒤 멈춰요. 운영 예시 최대 3회 뒤 보류·알림을 정하세요. 결과가 불명확한 발행은 post_id 조회부터 하고 새 POST를 반복하지 않아요.
