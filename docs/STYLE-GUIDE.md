# ReelsBook 문체·구성 기준 (확정)

작성: 2026-10-26, Claude Code. 사용자 선택: **안 A(수익 축 정의형) 뼈대 + 안 B(질문 답변) + 안 C(단계표)**. 이 기준은 인스타 편 이론편·실습편과 이후 유튜브 쇼츠 편 전체에 적용한다. `docs/style-guide.md`(Phase 8s 초안)보다 이 문서가 우선한다.

## 1. 왜 3장 샘플의 품질이 좋아졌나 (개편 전 → 후)

| # | 개편 전 원고의 문제 | 샘플에서 바뀐 점 | 원칙 |
|---|---|---|---|
| 1 | 작성자가 정리하고 싶은 개념(지급자·대가·장부)에서 출발했다. | 학습자가 실제로 묻는 질문("조회수 100만이면 얼마?")에서 출발했다. | **질문에서 출발** |
| 2 | 결론 없이 조건과 단서만 나열했다. | 첫 문장이 직답이다. 불리한 답(0원)도 그대로 말한다. | **결론 먼저** |
| 3 | 숫자를 피했다("단가 자료를 확보하지 못했다"). | 근거 있는 숫자를 찾아 크게 보여 주고 계산 예를 붙였다(쿠팡 3%: 5만 원×20건×3% = 3만 원). | **구체 숫자 + 계산 예** |
| 4 | 절마다 형식이 달라 비교가 어려웠다. | 축마다 같은 틀(정의 → 흐름 → 얼마 → 조건 → 언제부터 → 지금 할 일)을 반복했다. | **같은 틀 반복** |
| 5 | 문장마다 "미확인·별개·단정할 수 없다"를 붙였다. | 불확실성은 항목 끝 "확인할 점" 상자 하나에 모았다. | **주의는 한곳에** |
| 6 | 읽고 나서 무엇을 할지 없었다. | 항목마다 "지금 할 일" 한 줄로 끝냈다. | **행동으로 끝내기** |
| 7 | 회계·법률·연구 용어(적격, 현금 잔액, 계약, 범위)를 썼다. | 생활어로 바꿨다("남는 돈", "누가 돈을 보내나"). | **쉬운 말** |
| 8 | 작업 과정 용어(7r, PRAC-25, 원응답, 키트 계약, 실측 아님)가 본문에 노출됐다. | (샘플에도 일부 남음 → 이번 개편에서 완전히 제거) | **내부 용어 금지** |

## 2. 장 구성 틀 (이론편)

모든 이론 장은 다음 순서를 따른다. 기존 9단계 블록은 유지하되 학습자 친화 이름을 쓴다.

1. **먼저 답부터** (기존 '일상의 질문'): 이 장의 가장 큰 질문 하나와 굵은 직답 1~2문장. 하린·정 선배 대화는 2~3줄.
2. **한눈에 보기** (기존 '만져 보는 그림'): 이 장의 축/흐름을 한 장 그림으로. 클릭하면 해당 절로 이동.
3. **축별 설명** (기존 '원리', 안 A 뼈대): 이 장의 주제를 3~5개 축으로 나누고, 축마다 같은 틀을 반복한다.
   - 한 줄 정의 → 어떻게 되나(흐름) → 얼마나/어떤 기준(숫자와 계산 예) → 조건·정책 → 언제부터/언제 쓰나 → **지금 할 일**
   - 축 끝에 "확인할 점" 상자(선택, 2~3줄, 출처 각주).
   - 장마다 축 이름은 주제에 맞게 정한다(예: 2장 = 보이는 방식의 축: 추천 피드/팔로워 피드/검색/공유).
4. **해 보기** (기존 '시뮬레이터'): 학습자 질문에 답을 주는 도구 1개(많아야 2개). 결과는 숫자 하나 + 한 문장 해석.
5. **실제 사례**: 공개 사례 1~3개, "이 사례에서 배울 점" 한 줄씩.
6. **단계표** (안 C, 해당 장만): 팔로워·운영 기간·계정 단계에 따라 달라지는 내용이 있으면 단계별 표 1개. 가상 수치는 계산식 공개 + "가상" 표시, 예측처럼 쓰지 않는다.
7. **작업실 노트**: 생각 정리·기획 결과물만. 계정·도구 조작은 실습편 링크.
8. **자주 묻는 질문 5개** (안 B): docs/learner-questions.md의 해당 장 질문 5개에 굵은 한 줄 직답 + 2~3줄 + 관련 절 링크. 본문에서 이미 답한 것은 짧게 링크로.
9. **핵심 정리 3줄 + 퀴즈 3~4문항**.

분량: 개편 전보다 짧게(목표 70% 이하). 학습자 질문에 답하지 않는 문단은 삭제한다.

## 3. 문장 규칙

- 첫 문장 = 직답. "~입니다/~하세요"로 끝나는 단정문을 우선한다.
- 한 문장 한 정보. 60자 안팎. 괄호 속 부연 최소화.
- 숫자는 근거가 있으면 단정적으로, 근거가 약하면 "참고용 · 출처" 한 번만. 범위 숫자는 표로.
- 근거가 없으면 숫자를 지어내지 말고 **학습자가 직접 확인하는 방법**을 준다("내 프로페셔널 대시보드 > 수익화에서 확인하세요").
- 상충 정보: "공식 문서 안에서도 50건/100건으로 다르게 적혀 있어요. 안전하게 50건으로 잡으세요."처럼 **결론과 권장 행동**을 함께 준다.
- 출처 각주 [S000]는 문장 끝에 작게. 사실 ID(PRAC-, API- 등)는 본문에 쓰지 않는다(필요하면 각주 마크업 data 속성에만).
- 존댓말 "~해요/~합니다" 중 하나로 장 안에서 통일. 실습편은 "~해요/~하세요" 친근체, 이론편은 "~합니다" 기본.

### 금지어 → 대체어

| 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 지급자 / 대가 | 누가 돈을 보내나 / 무엇을 해 주고 받나 |
| 장부, 현금 잔액 | 수입·지출 메모, 남는 돈 |
| 적격, 적격성 | 받을 수 있는 조건 |
| 키트 계약, 로컬 키트 계약 | 스타터 키트가 만드는 파일 규칙 |
| 실측 아님, 시간 배분 예시 | 약 30분 (실습편 첫 페이지에 "시간은 대략이에요" 한 번) |
| 탐색 후보, 성공 화면을 본 것으로 서술하지 않습니다 | (삭제) |
| 미확인입니다 / 단정할 수 없습니다 (반복) | "확인할 점" 상자에 한 번, 대안 행동과 함께 |
| 7r, 7v, Phase, Hermes, 원응답, 조사자 | (본문 금지) "2026년 10월 조사 기준" 표기만 |
| 독립 확인을 완료하지 못했다, 공식 본문을 확보하지 못했다, 재열람이 차단됐다 | "공식 안내에서 아직 확인되지 않았어요. ○○에서 직접 확인하세요." |

## 4. 실습편 규칙

- 단계 틀(지금 하는 일 / 왜 / 따라 하기 / 이렇게 보이면 성공 / 이렇게 보이면? / Windows·macOS)은 유지한다.
- 앱 버튼 안내 표준 문구(사용자 지시). 메뉴 경로 옆에 한 번만:
  > 앱이 업데이트되면 버튼 이름이나 위치가 조금 다를 수 있어요. 최신 앱 화면에서 비슷한 이름의 버튼을 찾아 주세요. 못 찾겠으면 공식 도움말(링크)을 확인하세요.
- Phase 1c에서 확인된 실제 메뉴 이름이 있으면 그것을 쓰고, 없으면 "보통 이런 이름" 후보를 쓴다.
- 작성자 면책 문장(OS 탭은 실기기 성공을 뜻하지 않습니다 등)을 삭제한다. 대신 실습편 첫 페이지에 "화면은 기기·버전마다 다를 수 있어요" 한 번.
- 각 실습 시작에 "이 실습이 끝나면 내 손에 있는 것" 한 줄, 끝에 "다음 실습" 버튼.

## 5. 검수 기준 (리뷰어용 채점표)

장마다 아래를 모두 만족해야 통과다. 하나라도 아니면 고친다.

1. 해당 장의 학습자 질문 5개 각각에 대해 **첫 문장 직답 + 숫자 또는 예 + 할 일**이 본문이나 FAQ에 있다(엄격 판정: 관련 설명만 있으면 '부분'으로 불통과).
2. 금지어·내부 용어 0개(자동 검사).
3. 문장마다 붙은 단서 없음: "확인할 점" 상자 밖에서 "미확인/단정할 수 없/별개" 표현이 장당 2회 이하.
4. 축별 설명이 같은 틀을 반복한다.
5. 분량이 개편 전의 70% 이하(이론편).
6. 모든 숫자에 출처 각주 또는 "가상·계산식" 표시.
7. 처음 읽는 사람이 3분 안에 "그래서 나는 무엇을 하면 되나"를 말할 수 있다.

## 6. 시각자료 기준 (사용자 지시 2026-10-26)

사용자 원문: "억지로 이미지를 늘릴 필요는 없고, 시각자료가 있으면 좋은 내용은 적극적으로 활용하라." → **개수 기준은 없다.** 그림이 글보다 빨리·정확하게 이해되는 내용이면 반드시 그림으로 보여 주고, 글만으로 충분한 곳에는 넣지 않는다.

### 6.1 그림을 적극적으로 쓰는 곳
| 내용 | 그림 |
|---|---|
| 순서·흐름(제작 과정, 파이프라인, 게시 절차) | 흐름도·단계 띠(입력 → 서비스 → 출력) |
| 숫자 비교(수익·비용·조건·한도·단계표) | 막대·계단 차트, 시각화한 표 |
| 여러 선택지 비교(플랫폼·도구·요금제) | 비교 도식, 고르기 분기 그림 |
| 앱·웹 화면에서 어디를 누르나 | 직접 그린 단순 화면 틀 + 번호 동그라미(실제 UI 캡처·로고 복제 금지) |
| 결과물이 어떻게 생겨야 하나 | "이렇게 보이면 성공" 결과 예시, AI 생성 예시(프롬프트와 함께) |
| 좋은/나쁜 결과 차이 | 같은 크기 2칸 비교 + 차이 번호 |
| 구조(시스템 구성, 폴더, API 호출 순서, 상태 흐름) | 구성도·시퀀스·상태 그림 |
| 영상 감각(구도, 안전 영역, 타임라인, 음량) | 도식·키프레임 |

### 6.2 넣지 않는 것
- 본문을 되풀이할 뿐인 그림, 장마다 의무로 붙이는 장식 삽화, 개수를 채우려는 그림. 인물 삽화는 대화가 장면을 설명할 때만(쓴다면 기준 시트로 그림체 통일).

### 6.3 공통 규칙
- `<figure>` + `<figcaption>`(그림이 말하는 결론 한 문장) + 의미 있는 `alt`/SVG 제목. 복잡한 그림은 글 설명을 함께.
- SVG는 CSS 변수/`currentColor`로 라이트·다크 대응, 360px 폭에서 글자가 읽혀야 한다. 차트 숫자는 본문과 같은 근거, 캡션에 출처와 기준일.
- 래스터는 WebP 우선, 한 장 400KB 이하, `loading="lazy"`·`width/height` 지정.
- check_site는 개수를 세지 않고 figcaption·alt 누락만 검사한다.
